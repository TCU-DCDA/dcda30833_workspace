# LAB 12 — System Identity Translation

## Purpose

This lab asks a question you now have enough work to answer: **what makes a
system the same system?**

You will take one of your **own** earlier systems — from PROJECT 2, 3, 4, 5, or
6 — and rebuild it in a **different material**. A color system becomes a sound
system. A text system becomes a data system. A rhythm becomes a drawing.

You are not porting the output. You are porting the **rules**, and then finding
out which of them were ever really about the medium at all.

---

## Core Idea

Translate the logic, not the look.

If your original piece placed marks with a 10% probability gate and a fixed
palette, the translation keeps the 10% gate and the fixed set — but the set is
now four pitches, or four intervals, or four word lengths. What you must not do
is try to make the new version *look* or *sound* like the old one. That would be
imitation, and imitation is exactly what this lab is designed to rule out.

Then the question that matters: **is it still the same piece?**

There is no correct answer. There is only your account of what survived.

---

## Restrictions

You **must use**:

- One of **your own** completed systems as the source (PROJECT 2–6)
- A **different mode** as the destination:
    - image → sound
    - sound → text
    - text → data
    - data → image
    - or any other crossing, as long as it is a real crossing
- The **same rule structure** as the original — same probabilities, same
  constraints, same thresholds, same number of states

You **may not use**:

- A new system invented for this lab
- The same mode you started in (recoloring is not translating)
- Any attempt to reproduce the original's appearance in the new medium

## Precedent Worth Knowing

**Sol LeWitt's wall drawings** exist as written instructions. Different
draftspeople execute them, decades apart, and every execution differs — yet
everyone agrees it is the same work. LeWitt located the piece in the instruction
rather than in any drawing of it.

**Casey Reas's *Software Structures* (2004)** ran the experiment deliberately:
he took LeWitt-style descriptions and implemented each in several different
ways, then put the versions side by side. The [project and its
essay](https://artport.whitney.org/commissions/software-structures-2016/text.html)
are free at the Whitney's artport, and they are essentially this lab, done
carefully.

Both suggest an answer worth arguing with: the system is the work, and the
output is just one thing the system happened to do.

## The Note (This Is the Real Assignment)

Write **250–400 words**:

1. State the original rule structure plainly — as if writing a LeWitt
   instruction. Someone else should be able to implement it from your
   description.
2. Say what each rule *became* in the new medium, and why that correspondence
   and not another.
3. Name the rule that **would not translate**. There will be one — something
   that turned out to depend on the medium rather than on the logic. What was it
   actually about?
4. Answer the question: is the translation the same piece? Argue for your
   answer; do not hedge.

---

## Reflection (3–5 Sentences)

Answer briefly:

1. Did the translation reveal something about the original you had not noticed
   while building it?
2. Which version do you prefer — and does preferring one undermine your claim
   that they are the same system?
3. If someone re-implemented your written rules without seeing either version,
   how close do you think they would land?
